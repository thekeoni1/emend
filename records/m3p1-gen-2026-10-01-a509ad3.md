### Shared paths

- Open: `Package::open` (package.rs:3979) opens the archive. The central directory and the entry
  list are held; they are small, nine entries. `workbook()`, `content_types()`, `relationships()`
  and `styles()` each parse their part once into a model and cache it (package.rs Parts::workbook,
  Parts::content_types, Parts::relationships, Parts::styles). These parts are small on every tier.
- `Package::cells` (package.rs:4072) streams. It is a `Cells` iterator over `Archive::read(index)`,
  through `xml::Stream`. Stream's `Tee` keeps the bytes of the current token and compacts at 64 KiB
  (xml.rs:111, 118, `Tee::release_to`). `Stream::next` clears its event buffer per token
  (xml.rs:252). Memory is constant in the part's size.
- `Package::shared_strings` (package.rs:4046 -> Parts::shared_strings, `SharedStrings::read`)
  holds the whole table as `Vec<String>` (cells.rs:182, 228). No sample calls it. Only the
  non-sample operations `--shared-strings` (main.rs:4697) and `--cells` (main.rs:4799) do.
- Sheet-wide reads other than cells, all streaming and each a full pass over the part (no early
  exit found):
  - in the crate: `read_validations` (package.rs:15672, for `validations`) and `read_rules`
    (15493, for `conditional_formats`);
  - in the crate: `table_part_ids` (for `tables`, Parts::tables 6530) and `element_rel_id` (13719,
    for `drawing_of` 7215, `images`, and the comments and images records);
  - the tool's own passes over `read_part` + `Stream`: `sheet_counts` (main.rs:2849),
    `link_counts` (3096), `validation_container` (3294), `container_and_binding` (4231) and
    `root_children` (4410).
- `Package::write_to` (package.rs:5470 -> Parts::write_to 7747), entry by entry:
  - An edited worksheet streams: `rewrite_worksheet` / `rewrite_worksheet_from` (11230/11242)
    for cell, style, format, pane, merge, link, protection, validation, rule, table, comment and
    image edits, and `shift_worksheet` (16201) for a row or column shift. Each reads the input
    entry through `Stream` and writes the tokens through a `BufWriter` into a `TempFile`
    (`temp_for_part`, package.rs ~9070). The data held is in proportion to the EDITS (`Pending`
    edits and rows, `ColsBuffer`, `MergesBuffer`, `CountedBuffer`, `arrays`), not to the part.
  - Every replacement is then compressed by `compress_replacement` (archive.rs:1830), streaming
    the temporary file into a `zip::ZipWriter` over a second `TempFile`, with `large_file(true)`.
    `Made::copy_data` copies it into the output with `copy_exact`, a fixed 64 KiB heap buffer
    (archive.rs:250, 1655).
  - `styles` (`rewrite_styles` 9265), the workbook part (`rewrite_workbook_part` 9749), core
    properties (`rewrite_core` 12286), content types and rels (`rewrite_part` 9124) stream the
    same way. Each is small.
  - Comments and VML: `record_comments` (6838) reads an existing VML part whole
    (`read_to_end`, 6993). Drawings: `record_images` reads an existing drawing part whole
    (7303). The generated tiers have neither part, so the new parts are built in memory from the
    edits, which is small.
  - Untouched entries, sheet1 and tier D's sharedStrings.xml (166996261 bytes uncompressed, test.log's sst_file_size) included, are copied
    raw with `copy_exact` (archive.rs:974). The bytes are not decompressed or held.
  - Header values: a replaced entry's sizes go into the zip64 extra field when the input carries
    one (`put_value` archive.rs:1536, local header 1950-1962). Without one, a value over u32 is
    refused with "a replacement too large for a local header with no zip64 extra field". Tier
    C's sheet1 has the zip64 extra field (the generator forces it), so a rewritten tier C sheet
    is predicted to write.
- Temporary files: `TempFile::new` (archive.rs:1786) uses `env::temp_dir()`. The runner sets no
  TMPDIR, so this is /tmp, which is tmpfs on this box (11G, 9.6G free at survey time, by df; no log prints it). On tier
  C a sheet rewrite holds the uncompressed temporary file (about 4.7 GiB) and its compressed
  copy in tmpfs at once. That is host RAM, but it is not process address space or RSS, so the
  2048 MiB cap and peak_rss_kb do not see it.
- The tool's write: `write_package` (main.rs:4660) runs `Package::write_to` into a
  `BufWriter<File>` that is a temporary file beside the output, then renames it (`write_into`
  2957, and the inline equivalents).
- Read-back: every sample reopens its output from the file with `Package::open(BufReader)` and
  reads it again with the passes listed per sample.
- In-memory second write: five samples write the WHOLE package a second time, after one more
  removal, into `io::Cursor<Vec<u8>>` and reopen it from memory: validate (main.rs:3280), cf
  (3461), table (3758), comment (4086) and names (4476). This holds the entire output archive
  (compressed) in the tool's memory, with Vec doubling on growth. It is a tool-side hold through
  `Package::write_to`, not a crate read.

### Unsure, from the code alone

1. names on tier C: whether the Cursor's growth fails under 2048 MiB depends on tier C's
   archive size (written before the tiers existed; test.log now prints tier c's archive as
   1159829654 bytes, over 1 GiB, so the Cursor's last doubling would ask for 2 GiB) and on whether realloc can grow in place (mremap on glibc for the host; musl
   on i686). The exit form is also open: an allocation failure aborts (134); a kernel kill under
   tmpfs pressure would be 137.
2. Whether `rewrite_worksheet` refuses a cell at row 1048577 anywhere in the write. I found no
   grid check on `set_cell` or `set_cell_style` (package.rs:4234, 5909), and cells.rs:122 and
   320 say no sheet-size limit is enforced. I did not read every branch of `Pending` in
   rewrite_worksheet_from.
3. tmpfs capacity on tier C: the rewrite of sheet1 holds about 4.7 GiB uncompressed plus about
   1.1 GiB compressed in /tmp at once. /tmp had 9.6G free at survey time (df; no log prints it), but session scratch
   shares it. Two labels run one after the other, and TempFile's Drop frees each between runs,
   but a killed run leaves its temporaries behind (Drop does not run on SIGKILL).
4. The zip crate's reader on i686 for an entry over 4 GiB: `Archive::read` (archive.rs:775)
   returns `zip::read::ZipFile`. I did not trace the zip crate for any usize conversion of the
   entry size on a 32-bit target.
5. The read-back passes of comment_read_back and table_read_back are counted from the calls
   listed, not from every helper's body.
6. `remove_sheet`'s reachable walk reads rels only. I did not confirm that nothing in
   `chain_removals` or the content types walk reads sheet1.

## Findings for planning before P2

1. `--new-sample` overwrites its input under the runner. The runner
   passes `corpus/<id>.xlsx` as the first path
   (`scripts/passthrough-run.sh`, `input=` and the tool call), and
   `new_sample` writes `Package::new()`'s bytes to that path. Run as
   one of "25 samples" over the scale directory, it would replace the
   tier's workbook with the template workbook. `specs/0016` says the
   runner does not run this operation over the corpus. P2 needs a
   ruling: 24 samples, or a copy of the input per run.
2. Temporary files of a rewrite go to `env::temp_dir()`, which is
   `/tmp`, a tmpfs on this box (11G, 9.6G free when the survey was
   read, by df; no log prints it). On tier c a sheet rewrite holds the uncompressed temporary
   (about 4.7 GiB) and its compressed copy there at once. That memory
   is invisible to the address-space cap and to peak RSS, and a run
   killed by the cap or the timeout leaves its temporaries behind.
   P2 needs a ruling on `TMPDIR` for the runs (a directory on the
   disk) and on recording the temporaries' size.
3. Six samples (edit, style, font, border, date, formula) add a row
   one past the sheet's last; on tier c that is row 1048577, past the
   grid, and `set_cell` records it with no check. Predicted `ok` with
   an output Excel would refuse to open as written; a defect or a
   limit for planning to classify when P2 measures it.
4. Seven samples (format, validate, cf, scale, table, comment, image)
   are predicted refused on tier c at the recording call, and
   insert-rows at the write. Tier c then measures fewer write paths
   than tiers a, b and d; the prediction is recorded here, not
   changed.
