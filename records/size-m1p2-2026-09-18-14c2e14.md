## A stored-replacement mode, as a proposal

A consumer that accepts larger output files could write replacements STORED
rather than deflated, and skip the encoder. What that would save is measured
here: the encoder and the crate's writer are the whole difference between
`probe-zip-xml-write` and `probe-zip-xml`, 72788 section bytes and
73728 file bytes. What the layer would need is a replacement written
with method 0, which the writer's local-header and data-descriptor code
already handles, since a stored entry is the form every passed-through entry
already takes. It is a proposal for the maintainer, not work in this part, and
no code for it exists.

## Reading these figures

File sizes on this target change in whole 4096-byte steps. They are not
themselves whole pages: all seven probes leave the same remainder, 2596 bytes,
modulo 4096, so it is every DIFFERENCE between them that is a whole number of
pages. A change under a page is therefore invisible in the file size, while
the section totals, from `size -A`, resolve to the byte. Both are given for
every figure above.
